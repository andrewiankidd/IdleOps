# Backlog

Forward-looking work list for IdleOps. Items are organized around the [project vision](../README.md): **CI-regenerated, TTS-narrated video walkthroughs that keep app docs perpetually in sync.**

For internal/code-level tech debt, see [.context/tech-debt.md](../.context/tech-debt.md). This file is the product-facing backlog — what we want to build and why it matters.

## Critical path: video docs in CI

The flagship use case is "run `playbk` in CI, get a narrated MP4 out." The pieces that block it:

1. **`speak` action in playbk** — `spkbak` already does TTS; needs a first-class playbk action so scripts can declare narration alongside steps instead of shelling out.
2. **Narration ↔ video sync model** — decide how step narration becomes a timed audio track that aligns with `outcap` video. Candidates:
   - (a) Pre-render per-step narration WAVs, mix in post against step timestamps
   - (b) Speak live during capture so `audcap` records it naturally
   - (c) Generate subtitles + audio as separate artifacts, mux in post
3. **CI runner story** — document a working setup for a Windows runner with desktop session, audio device, and OCR available. GitHub Actions `windows-latest` is the obvious first target; capture what does/doesn't work.
4. **End-to-end reference walkthrough** — ship one full narrated walkthrough of a real app (crosspose is the obvious candidate) generated by a single `.idleops.yaml` script in CI. This is the proof point.

## Per-tool follow-ups

### playbk

- Honor `text:` field on `wait-window` action — currently a silent no-op (full repro in [.context/tech-debt.md](../.context/tech-debt.md))
- New `action: speak` wrapping `spkbak` (see critical path above)
- Step-level `narration:` field as sugar for a paired `speak` action
- Script variables / conditionals / loops (deferred from [.context/recommendations.md](../.context/recommendations.md))
- Parallel step execution

### txtfnd

- Tesseract fallback when `Windows.Media.Ocr` returns zero matches — observed missing stylized text (Town Spirit "Start" button)
- `fallback_coords` on `click-text` action so playbooks aren't forced into raw `exec` when OCR misses

### vidcap / outcap

- Linux/macOS window capture (xdotool/xwininfo on Linux, CGWindowListCreateImage on macOS)
- Document cursor visibility, DPI, and multi-monitor edge cases
- `outcap` integration tests beyond option parsing

### Cross-platform

- `spkbak` is Windows-only — pick a cross-platform TTS path (system voices on macOS `say`, `espeak`/`festival` on Linux, or a cloud TTS option)
- `inpctl` is Windows-only — Linux/macOS equivalents (`xdotool`, CGEvent) if cross-platform automation becomes a goal

### Test gaps

- `waitfr`, `imgfnd`, `spkbak` test projects exist but have no tests yet (require live desktop / hardware)
- `inpctl` only covers window matching and key mapping, not actual input sending
- `audcap`, `vidcap`, `playbk` tests are Windows-only and require real hardware

## Distribution

- Portable single-file executables per tool (ffmpeg aesthetic) instead of `dotnet run`
- Release zip bundling all tools
- Versioned releases on GitHub with checksummed binaries

## Open questions

- Should narration live inline in `.idleops.yaml` (`speak:` on each step) or in a parallel narration file keyed by step name? Inline is simpler; parallel makes localization easier.
- How do walkthrough scripts version alongside the app — same repo, separate repo, git submodule?
- For OCR-sensitive walkthroughs, is `imgfnd` (reference-image matching) a better default than `txtfnd` (OCR)? Tradeoff: imgfnd is DPI/theme-fragile, txtfnd is font-fragile.
- TTS voice selection: ship a fixed voice for consistency across releases, or let scripts choose?
